# SIM Exports — design decisions so far

Working folder for the export flow. Companion to `../SIM Inventory/`, which holds the import side.

**Environment**

| Inventory template | `SIM_Data_Validation_DEMO.xlsx` (in Documents) |

---

## Decided

**One flow, `ExportType` parameter.** `Inventory` or `Requests`. Shared staging, logging, catch
scope and delivery; only the data shaping differs. Your existing inventory export becomes a
branch inside it.

**Delivery: sync under a threshold, email above it.** Small exports return a URL and PowerApps
launches it immediately. Large ones respond "we'll email it" and finish in the background. A
PowerApps flow call times out around 120 seconds, so a 60,000-row inventory export cannot be
synchronous — but making every export async would punish the 200-row case for the sake of the
rare big one.

**Volume:** Inventory up to 60,000. Requests up to 10,000 per country.

**Requests export is a provider handover workbook, not a data dump.** The local admin sends it
to the country's provider, who fills in the operational detail — phone number, ICC_ID, start
date — and sends it back. That makes it a round-trip document, so it gets the template
treatment: validated fill-in columns, protected request columns.

**One sheet per request type.** New SIM, Terminate, Swap, Change plan and so on each get their
own tab carrying only the columns that type needs. A provider looking at eight columns where
three apply will fill the wrong ones.

**Sheet protection on, no password.** Only the provider fill-in columns are unlocked. This stops
a RequestID or employee name being altered in transit, which would break the return-leg import.
No password: it prevents accidents rather than determined edits, and a locked-out provider is a
support call you don't want.

**The export stays read-only.** No stamping of `ExportedOn` on the Order List, no
`Approved → Sent to provider` status transition. Exporting reads; it does not write back.

**Audit lives in an Export Log list** — date, who, country, export type, row counts, link to the
file. Schema in `02_Export_Log.md`.

One consequence to be aware of rather than act on: nothing prevents the same approved request
being exported twice, so a provider could provision the same SIM twice. The log makes that
*detectable* — two Requests exports for the same country days apart, with the second showing the
same row count — but not *prevented*. If it ever happens for real, §1 of `01_Edge_Cases.md` has
the fix ready.

## Consequence worth planning for now

The provider sends the workbook **back**. That return leg needs a flow that reads the completed
sheets, validates what the provider typed, updates the Order List, and creates the resulting
Global SIM Inventory rows.

Designing the handover sheet for that now costs nothing. Retrofitting it later means asking
providers to switch to a new format. Concretely, it means:

- **A stable RequestID column** on every sheet, protected, used to match on the way back
- **Fill-in columns validated at source** — the same ICC_ID, PhoneNr and StartDate rules already
  built and tested for the inventory workbook, reused verbatim
- **A hidden metadata row or sheet** carrying the export's RunId and country, so the import can
  verify the file came from a real export rather than being hand-assembled

## Still open

**Delivery mechanism.** `Launch(download.aspx?SourceUrl=…)` works but depends on the user having
read access to the library, and a permissions gap surfaces as a browser error rather than
anything the app can catch. Alternatives to weigh once the rest is settled — a sharing link
generated by the flow, or emailing the file as an attachment.

**Needed before the template can be built:** the Global Order List column schema, and which
columns the provider fills for each request type.
